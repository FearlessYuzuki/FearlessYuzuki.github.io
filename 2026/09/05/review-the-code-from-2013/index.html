这里是判断角色是否不应该被操控。Source 是按 tick 来进行的，而 CheckParameters() 在每一个 tick 中都会发生——比如 64tick 服务器，这个检测每秒正好 64 次；只要有一次角色处于死亡状态，指令输入就会被清零。

这一大段是给后坐力控制来回复视角的，不然视角就会一直上跳而不回复。（这里我也很震惊——毕竟 CS 也有 3000+ 小时，一直认为 64tick 压枪和 128tick 压枪没区别，而且普遍认为 128 更”好压枪”。其实确实是这样：128tick 下视角回复更平滑，体感就是更流畅。但这一套不适用于 CS2 的 Subtick 机制，目前我还没完全搞明白 Subtick 具体是怎样的。）

这里是服务器客户端同步：服务器接收的角度只处于 [-180,180] 区间内，但客户端的实时视角转动其实能够超过这个范围（比如 270 度很容易触发），一旦大于 180.f 就直接减 360 度，自然就回到了 [-180,180]（该区间长度正好是 360）。本质是视角归一化。

其实这样看起来，起源引擎的预测机制还是很复杂的，但也从侧面印证了一点：当时比较出名的外挂都会带回溯（回溯预测）功能，本质就是靠这个预测机制做到的。视角上游戏只会有一个模型，但身位是可以在预测前和补后的，因此存在这个功能。我觉得任何 FPS 游戏只要包含预测机制，就可以通过预测机制来实现一些功能。

剖析 PlayerMove()

在玩家移动被调用时，这里初始化这两个速度。主要有两个目的：一是把这个速度传递出去（out***），二是把它归零——mv 这个指针在 gamemovement 中被使用的次数超出想象的多，这么做是为了避免数据污染（脏数据）。

每帧调用移动时，假设没有接触任何东西，清空 timer（Timer 与角色移动的状态计时器相关内容），然后获取移动角度。

字面意思：我们卡住没有，玩家卡住就不走这里了。

这里是关于梯子的问题。从游戏里就看得出来，梯子会有一些奇奇怪怪的 bug，比如 KZ 图里很经典的 ladder jump——其实是因为起源对梯子这个特殊物件有些头痛，所以单独把梯子拎出来处理。

这里是 PlayerMove() 中我认为很重要的部分：通过 player 指针得到玩家当前状态，再来分配动作。接下来我们顺藤摸瓜去看 FullWalkMove()。

这里同样用到了 0.5。我借助 AI 分析并综合了自己的理解，这是 Valve 故意对重力这样写的。更准确的说法是：

Source 使用了一个”分裂 / 分步的重力更新方式”，把重力加速度在一个 movement tick 的开始和结束各施加一半。 这在数值积分上相当于**半隐式欧拉（symplectic Euler）**的修正思路——更符合”这一整帧中重力逐渐作用”的直觉。

如果在一开始就已经把速度计算完了，那么整个帧的速度在整帧中都是被重力完全影响后的速度，跳起的抛物线顶点位置就会有偏差。

接下来继续看 FullWalkMove()：一开始写的是水中的情况——如果在水中，会检测是否跳跃、是否能够离开水面；同时跳跃的事件也会有一个 Timer 触发。这里不深究水中和梯子等特殊情况，只讨论平地上的跳跃和行走：

之前我已经尝试过将基础的摩擦力应用到 UE 上（参考 gamemovement.cpp -> Friction()）。这里学到的是：摩擦力的作用其实是在基础速度附加之前就已处理，同时也要考虑摩擦力在传送带上的影响（相对传送带静止时，速度不会被降慢）。

应用摩擦力之后，检测速度是否有效。至于速度的有效怎么判断，我认为不同场景有不同的写法，没必要完全参考，这里也不赘述。

勘误（自查修正）

以下是原文中最早版本里我自查发现的明显错误，保留在文末便于对照：

  1. “在 UE 里我们为了计算精度，统一使用 double 了” — 错误。UE 默认 FVector 是 float（单精度），并非 double。UE5 中 FVector::RealType 默认仍是 float，仅双精度构建版本才切换为 double。准确表述应为”UE 使用 float 精度向量”。
  2. “欧拉积分（第一类/第二类，B函数/Γ函数）” — 概念混淆。数值积分中真正使用的是欧拉积分法（Euler integration method，显式/半隐式欧拉算法），与数学分析中的”欧拉积分（B函数/Γ函数）”是完全不同的概念。本文 Split-Gravity 的理解应该对应半隐式欧拉（symplectic Euler），与 B 函数无关。
  3. “64tick 每秒检测至少 64 次” — 表述错误。64tick 就是每秒恰好 64 次，不存在”至少”。
  4. 原文若干错别字（如”参口SSG08”应为”比如”）已随手订正。
