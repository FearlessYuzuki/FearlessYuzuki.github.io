从零构建 Windows 双屏分辨率切换工具：C#、EDID 与那些坑

项目开源：FearlessYuzuki/Easy-Resolution-Changer
本篇文章是对该项目开发过程的完整技术复盘。

AI 辅助声明：本文项目（及其开发、调试、Git 发布流程）由 DeepSeek-V4-Flash-Vision-Exp 模型通过 opencode CLI 辅助完成，人负责需求描述与界面验收。README 中附有完整 Vibe Coding 数据：消耗 ¥1.16、105 次 API 请求、8,843,432 tokens。

起因很简单：手上有两台 1080p 显示器（一台 240Hz 主屏、一台 165Hz 副屏），经常需要在”高刷游戏”和”日常省电”等方案间来回切，Windows 自带的设置要点好几层菜单。于是想做一个一键切换的小工具，顺手练一下 Windows 系统编程——结果发现，看似简单的”改分辨率”，背后全是细节。

需求还原

  • 界面：Mac 风格圆角窗口，左右两块显示器卡片（图标 + 型号 + 下拉框）
  • 下拉框只列系统真实支持的分辨率/刷新率模式（不是瞎编的组合）
  • 三个按钮：应用（临时）、保存（应用 + 持久化）、恢复（还原启动时状态）
  • 能显示显示器真实型号（从 EDID 读，而不是”Generic PnP Monitor”这种废物名字）

架构

纯 C# + WPF（代码构建 UI，无 XAML），目标 .NET Framework 4.8——因为 csc.exe 是系统自带的最小编译方案，不需要装 VS 就能出 exe：

技术点 1：枚举显示器

核心 API 来自 user32.dll 的 EnumDisplayDevices + EnumDisplaySettings。第一级枚举显卡适配器，通过 DISPLAY_DEVICE_ATTACHED_TO_DESKTOP（0x1）筛选真实接入的显示器，跳过未连接的虚拟适配器（如 NVIDIA GameViewer 会创建十几条未接入的设备，全是障眼法）：

坑 #1：P/Invoke 的 CharSet 必须对齐

第一版崩溃点：DllImport 没写 CharSet，默认 ANTI 版本 EnumDisplayDevicesA 被调用，而结构体却是 Unicode 布局——返回的数据全变成乱码（像 屜尮?偓??），甚至”成功”枚举出 14 个假设备。

教训：DllImport("user32.dll", CharSet = CharSet.Unicode) 必须显式声明，且 DEVMODE/DISPLAY_DEVICE 结构体的 CharSet 保持一致。

另外注意：设备名传给 EnumDisplaySettings 时要带 \\.\ 前缀（\\.\DISPLAY2），只写 DISPLAY2 会静默失败。

技术点 2：模式枚举（分辨率列表）

EnumDisplaySettings 从 i = 0 开始枚举所有模式（0 是注册表模式），每个模式是一个 DEVMODE，包含宽、高、刷新率、色深。由于驱动会重复上报同一模式（刷新率 119/120 都是邻居），要按 WxH@Hz 去重：

最后按面积降序、刷新率降序排序，UI 里第一项永远是最常选的那个。

小发现：Samsung 240Hz 主屏支持 每个分辨率 都有 240Hz 选项（1280x720@240、1366x768@240……），AOC 副屏则最高只有 165Hz——EDID 的能力差异一目了然。

技术点 3：EDID 解析显示器型号

第二级 EnumDisplayDevices 拿到的 DeviceString 永远是 “Generic PnP Monitor”，得自己啃 EDID。

两条路：

  1. Win32: EnumDisplayDevices 第二级的 DeviceID 里有厂商代码（MONITOR\SKG2512 → SKG），但只有一个三字符代码
  2. 注册表: HKLM\SYSTEM\CurrentControlSet\Enum\DISPLAY\<型号>\<实例>\Device Parameters\EDID（无需管理员权限），是完整 128/256/384 字节 EDID

策略：从 DeviceID 提取厂商码（如 SKG），遍历注册表所有 EDID，匹配厂商码后解析 0xFC 显示器名描述符。这样能应对多显示器串号问题。

坑 #2：EDID 描述符的偏移

EDID 里显示器名描述符的标签位置，我先后试了”块起始 +4”、”块起始 +6”，全都不对。最后还是老实 dump 十六进制才看清真实布局：

标签（FC/FD/FF）实际位于描述符块偏移 +3 处，名称从 +5 开始。稳妥做法是直接扫描 00 00 00 FC 00 字节模式，而不是依赖理论偏移。

最终成品识别出：Samsung H25T7-3（主屏 240Hz） 和 AOC P24A2G（副屏 165Hz），名字直接显示在卡片上。

技术点 4：切换分辨率

写操作就是 ChangeDisplaySettingsEx：

  • CDS_UPDATEREGISTRY：写入注册表，重启后保持（对应”保存”按钮）
  • 不带 flag：仅当前会话临时生效（对应”应用”按钮）
  • 返回值 DISP_CHANGE_BADMODE (-2) 说明模式不在列表里——所以列表必须是真实枚举出来的

UI：WPF 纯代码构建的 Mac 风格窗口

用代码（FrameworkElementFactory）而不是 XAML 构建模板，两条重要结论：

  • Border 的 CornerRadius 不裁剪子元素！圆角只是背景的形状，子控件照样方角渲染。标题栏的方角实色矩形会像”凸起”一样盖住窗口圆角——需要在内容容器上加 RectangleGeometry 的 Clip，并在 SizeChanged 里更新尺寸
  • Grid 的子元素必须显式 Grid.SetRow，忘了的话全挤在第一行互相重叠（第一次运行 UI”完全错位”就是这个原因）

配色走 macOS 那一套：背景 #F5F5F7、卡片白 + #E5E5EA 细边框、主色 #007AFF（系统蓝）、红黄绿交通灯 #FF5F57/#FEBC2E/#28C840。

坑 #3：C# 5 兼容性

系统自带的 csc.exe（v4.0.30319）是 C# 5 编译器——不支持表达式体方法（=>）、不支持 pattern matching（is Type x）、不支持内联 out 变量（out string sv）。全都要改写。要么改用 Roslyn，要么老实写 C# 5 语法。

最终效果

  • 主屏卡片：显示器 1 · Samsung H25T7-3 · 主屏 · 1920×1080 @ 240Hz
  • 副屏卡片：显示器 2 · AOC P24A2G · 1920×1080 @ 165Hz
  • 下拉框就是系统模式列表，一键应用/保存/恢复

复现与扩展

扩展方向：托盘常驻 + 全局热键、双屏组合方案（一键切换整套配置）、NVIDIA 自定义分辨率注入。
